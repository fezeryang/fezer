最近我在学校 AI 平台上创建了一个 **Ollama 实例**，目标很明确：

希望把远端服务器上的大模型能力，接入到自己本地 Windows 电脑中的 **VSCode、Python 脚本以及其他开发工具** 中使用。

最初，我以为这件事会非常简单——平台既然已经提供了外部 API 地址，那本地程序直接请求这个地址就可以了。

但实际操作下来，我发现这个过程并不是"一步成功"，而是经历了：

- 理解平台提供的三种外部入口
- 区分 SSH、WebUI、API 三者的用途
- 排查平台 API 的 502 问题
- 建立 SSH 隧道作为稳定兜底方案
- 最终重新测试平台 API，并确认它已经可以直接使用

这篇文章就完整总结一下这个过程，以及最终形成的接入方案。

---

## 一、背景：为什么要在远端部署 Ollama

在本地电脑上直接运行大模型，通常会受到显存、内存、存储空间和算力的限制。

而学校 AI 平台提供了现成的远端实例环境，可以直接部署 Ollama，并加载多个大模型。因此，更合理的思路不是把模型"搬到本地"，而是：

**让模型运行在远端实例中，把本地开发环境作为调用端。**

这样做的优势很明显：

- 模型运行依赖远端算力
- 本地只负责写代码和发请求
- VSCode、Python、脚本、Agent 工具都可以统一接入
- 本地不需要承担模型运行压力

因此，本质上这不是"本地部署模型"，而是：

**本地开发，远端推理。**

---

## 二、平台提供的三种外部连接方式

学校 AI 平台给 Ollama 实例提供了三种外部访问方式：

- **SSH**
- **WebUI**
- **API**

一开始如果不理解这三者的区别，很容易走弯路。

从实际用途来看，它们分别对应三个不同层级。

### 1. SSH：远程管理入口

SSH 对应的是远端实例的运维与控制入口。

它的主要作用包括：

- 登录远端实例
- 执行 `ollama list`、`ollama run` 等命令
- 查看端口、进程、日志
- 修改环境变量
- 建立 SSH 本地端口转发

因此，SSH 更像是一个**控制面入口**，适合管理和排障，而不是直接提供模型调用服务。

### 2. WebUI：浏览器中的人工交互入口

WebUI 更适合人直接在浏览器中与模型对话。

它的定位类似于一个网页聊天窗口，适合：

- 临时测试模型效果
- 快速查看回复风格
- 做人工交互验证

但 WebUI 并不适合作为 VSCode、Python、脚本系统的底层接口，因此它更偏向于**展示层 / 交互层**。

### 3. API：程序调用入口

API 才是真正意义上的模型服务出口。

对于本地开发者而言，最有价值的并不是 WebUI，而是 API。

因为：

- Python 脚本调用的是 API
- VSCode 插件或本地工具调用的也是 API
- Agent、自动化流程、工作流系统接的还是 API

换句话说，真正承载大模型能力的，是 **API**。

从专业角度总结，这三者的分工可以概括为：

- **SSH：控制面**
- **WebUI：交互面**
- **API：服务面**

## 三、最初的尝试：直接调用平台暴露的 API

既然平台已经给出了外部 API 地址，那么最自然的想法就是：

直接让本地 Python 或 VSCode 请求这个 API。

例如，最开始的测试思路就是：

- 用 `/api/tags` 查询模型列表
- 用 `/api/chat` 发起聊天请求

这本来应该是最直接的路线。

但第一次测试时，实际结果并不顺利：

调用平台 API 时曾出现过 **502 Bad Gateway**。

这个错误说明：

- 请求已经到达平台网关
- 但网关到后端 Ollama 服务的转发环节出现了问题

也就是说，当时的问题并不在本地 Python 代码，而在于：

**平台 API 暴露链路是否真正可用，还不能直接下结论。**

---

## 四、排查过程：先确认远端 Ollama 是否正常

当平台 API 调用失败时，最重要的不是一味修改本地代码，而是先拆分问题层级。

我当时做的判断逻辑是：

### 第一层：远端实例本机 API 是否正常

如果远端实例本机访问 `127.0.0.1:11434` 都失败，那说明 Ollama 本身就有问题。

### 第二层：平台外部 API 是否正常

如果远端本机正常，但平台 API 异常，那么问题就在平台暴露层。

### 第三层：本地开发环境调用是否正常

如果平台 API 正常，本地 Python 仍然失败，那么问题就在本地环境配置。

这个拆解非常重要，因为它能避免把多个问题混在一起。

最终验证结果表明：

- **远端 Ollama 本机正常**
- 模型服务本身是可用的
- 问题并不在模型运行层，而在外部接入层

---

## 五、第一套稳定方案：通过 SSH 隧道接入本地

在平台 API 一度不稳定的情况下，最稳的方式其实不是继续死磕外部 API，而是：

**通过 SSH 本地端口转发，把远端 Ollama 映射到本地。**

这一步的核心思路是：

- 远端实例中的 Ollama 仍然运行在 `11434`
- 本地 Windows 电脑通过 SSH 建立一个隧道
- 把远端 `11434` 映射到本地某个端口，例如 `11435`
- 本地所有 Python / VSCode 工具统一请求本地端口

这样一来，本地程序虽然表面上访问的是：

```
http://127.0.0.1:11435
```

但实际上，请求会通过 SSH 隧道转发到远端实例中的 Ollama。

### 这种方式的本质

这相当于把远端模型服务"伪装"成本地模型服务。

从开发体验上看，它和本地运行 Ollama 很像，但实际推理仍然发生在远端服务器。

### 这种方案的优势

SSH 隧道的优点非常明显：

- 不依赖平台外部 API 网关是否稳定
- 本地开发工具统一走 localhost，接入非常自然
- 对 VSCode、Python、CLI 工具都很友好
- 安全性更高，不需要额外暴露公网服务
- 出现问题时更容易定位

因此，在整个排查过程中，SSH 隧道成为了一套**非常重要的兜底方案**。

---

## 六、本地端口为什么从 11434 改为 11435

在建立 SSH 隧道时，一开始尝试的是直接把远端 `11434` 映射到本地 `11434`。

但实际报错表明，本地 `11434` 已经被占用，或者当前环境不允许绑定这个端口。

这时最直接的解决方法不是继续死磕原端口，而是：

**换一个本地端口，例如 `11435`。**

于是最终采用的方式变成：

- 远端 Ollama：`127.0.0.1:11434`
- 本地转发端口：`127.0.0.1:11435`

从此以后，本地程序统一请求 `11435` 即可。

这个细节很小，但非常重要，因为它说明：

**SSH 隧道失败，不一定是远端有问题，也可能只是本地端口冲突。**

---

## 七、重新测试平台 API：这一次成功了

在通过 SSH 隧道打通本地调用链路之后，我没有立刻放弃平台 API。

相反，我重新按照更规范的方式，对平台 API 做了分层测试。

### 测试结论

最终结果非常清楚：

- 远端实例本机 API 正常
- 本地 Windows 直连平台 API 的 `/api/tags` 成功
- 重新调整测试方式后，`/api/chat` 也成功
- Python 侧调用也最终成功

这说明：

**平台 API 本身并不是永久不可用，而是前期测试方式和环境因素导致了误判。**

---

## 八、为什么 PowerShell 测试 `/api/chat` 一开始会失败

这里有一个非常容易踩坑的地方：

在 Windows PowerShell 中，直接手写 `curl.exe -d "{\"model\":\"...\"}"` 这种 JSON 请求，极其容易出错。

最初我在 PowerShell 里直接写 JSON 字符串，结果返回：

- JSON 解析错误
- 转义字符错误
- URL 解析异常

后来才确认，这并不是平台 API 的问题，而是：

**PowerShell 对 JSON 字符串转义的处理很容易把请求体写坏。**

因此，更稳的方式不是手写复杂转义，而是：

- 用 PowerShell 自己生成 JSON
- 或者直接用 Python `requests`
- 或者用 `Invoke-RestMethod`

这次排查给我一个非常实际的经验：

**命令行测试失败，不一定意味着服务端失败，也可能只是客户端转义写错了。**

---

## 九、为什么 Python 一开始失败

Python 的失败原因也并不一定在远端 API 本身。

在这种场景下，Python 失败通常有几个常见可能：

- Python 里使用了错误的 Base URL
- 代码还在请求旧的 SSH 隧道地址
- 系统代理环境变量干扰了 `requests`
- 本地网络环境与 PowerShell 测试环境不一致

后来通过重新梳理 Base URL、关闭环境代理继承、规范化请求方式，Python 测试也成功了。

这说明一点：

**本地 Python 是否能成功，并不只取决于远端 API 本身，还取决于本地开发环境是否干净。**

---

## 十、最终形成的两套可用方案

经过完整测试后，我最终确认了两套都能成立的方案。

### 方案一：直接使用平台 API

这种方案适合平台 API 稳定可用时使用。

本地 Python / VSCode 直接请求平台提供的 API 地址即可。

优点是：

- 不需要额外开 SSH 隧道
- 配置更简单
- 更接近"标准远端调用"

适合：

- 本地开发环境较稳定
- 平台网关工作正常
- 不需要完全依赖 localhost 的工具

### 方案二：通过 SSH 隧道映射到本地

这种方案适合作为稳定兜底。

优点是：

- 不依赖平台外部 API 是否稳定
- 本地开发统一使用 localhost
- 和本地 Ollama 使用方式几乎一致
- 对很多本地工具更友好

适合：

- 平台 API 偶发不稳定
- 某些工具只能配置 localhost
- 希望本地环境尽量统一
