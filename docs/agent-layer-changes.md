# Agent 层改造总结（Harness 化 + 3D 简历产品化）

> 时间：2026-09-13 ~ 09-14 ｜ 范围：`server/agents/**`、`server/routes/**`、`server/_core/**`、`client/src/**`、`drizzle/**`
> 上游文档：`docs/harness-and-jianli-roadmap.md`（计划与逐期进度）、`AGENT_ARCHITECTURE.md`（当前架构边界）

---

## 一、改造前是什么样

Agent 层本质上是一个**一次请求一次响应**的编排器：

- 调用链是 `routes → orchestrator → supervisor → expert → _core/llm`，没有运行时层
- 一次调用没有身份：没有 runId/threadId，日志里无法引用"某一次执行"
- 没有事件：调用方只能等到最后拿到一段文本，中间做了什么（调了哪些工具、花了多久）完全不可见
- 没有会话：多轮上下文由**客户端**每次上送，服务端无状态
- 没有预算与取消：唯一的限制是工具循环 3 次；客户端断开不会停止后面的工作，token 照烧
- 没有计量：`invokeLLM` 一直返回 usage，但全库无人读取
- **工具面有死代码**：注册 16 个工具，白名单只能触达 10 个（6 个永远调不到）
- 三层专家包装（`expert/index.ts` + 6 个 `*-agent.ts`）零消费者，纯透传
- 路由各自实现一遍 e2e mock、trace、错误映射

一句话：**有引擎，没有运行时。**

---

## 二、现在的分层

```text
调用方（Web 路由 / 3D 地图 / 未来的后台与脚本）
        │  只认一个入口：runAgent(request)
        ▼
server/agents/harness/        运行时层（新增）
        │  run 身份、事件、预算与取消、会话、计量、错误分类
        ▼
orchestrator → supervisor → expert → _core/llm     引擎层（结构未动）
        │
        ├─ tools / rag / spatial / relations         支撑层
        └─ _core 基础能力（事件汇 / 运行控制 / 计量 / trace / 模型客户端）
```

**核心原则：harness 不重复实现编排。** 它包在既有三层外面，负责"运行"而不是"思考"。

## 三、Agent 层的具体改动

### 1. 三份契约（先冻结，再实现）

| 契约       | 位置                          | 作用                                                                                         |
| ---------- | ----------------------------- | -------------------------------------------------------------------------------------------- |
| 运行事件   | `shared/src/schemas/run.ts`   | 10 种 `RunEvent`：run/step/agent/tool/text 生命周期；`run.finished` / `run.error` 是终止事件 |
| 会话与卡片 | `shared/src/schemas/agent.ts` | 请求侧的会话历史与 threadId；响应侧的内容卡片；`UiAction` 扩展                               |
| 错误分类   | `RunErrorCode`                | provider 不可用 / 预算耗尽 / 已取消 / 输入非法 / 内部错误 → 路由映射 HTTP                    |

事件协议是**一份**：SSE 路由、未来的地图主动导览、后台任务、CLI 都用它，路由只负责把它映射成 SSE 帧。

### 2. 三条 AsyncLocalStorage 通道（而不是回调透传）

专家工具循环跑在编排图的**单个节点内部**，`streamEvents()` 看不到工具级事件。因此运行时能力通过 ALS 提供：

- **事件汇**（`_core/run-events.ts`）：专家层直接发事件，不必把回调穿过四层签名
- **运行控制**（`_core/run-control.ts`）：取消信号、工具循环上限、流式开关
- **计量累加**（`_core/run-usage.ts`）：token、工具调用、provider 回退次数

它们与既有的 trace 上下文同族，都放在 `_core` —— 因为专家层必须**向下**读取它们，而"专家层 import harness"是反向依赖（改造中确实抓到一起这类违规并修掉）。

### 3. 取消是真的取消

- 墙钟超时或调用方取消 → abort 运行控制器 → 信号经 ALS 合并进 `invokeLLM` 的 fetch
- **取消不再触发 provider 回退**（过去 AbortError 被当成超时可重试，用户取消要付一次完整重试的代价）
- 分类由 harness 决定：预算耗尽与用户取消是不同的终止事件，调用方据此区分"超时"与"你取消了"
- 3D 聊天里的取消按钮因此真的能停掉服务端请求

### 4. 会话（thread）

- 表：`threads` / `thread_turns`（迁移 `0003`）
- **DB 优先、进程内存兜底**：会话属于尽力而为的数据，数据库不可用时也不能让请求失败
- 服务端历史优先于客户端上送的历史（前者是助手真实说过的内容）
- 信任边界：每 thread 40 轮、每轮 4000 字符
- 配套：`GET /api/chat/thread/:threadId` 供"继续上次对话"恢复消息列表

### 5. 计量

`RunUsage` 曾长期是 0 占位。现在每次 run 报告真实的 prompt/completion token、工具调用次数（含服务端预取）、provider 回退次数与墙钟耗时。

### 6. e2e mock 下移到运行时入口

过去 mock 写在每个路由里 —— 未来任何新调用方都得记着自己加。现在 `runAgent` 入口处接管，且产出**完整事件流**，所以流式路径在 e2e 下也正常。

### 7. 边界收敛（删掉的死代码）

| 删除物                 | 数量   | 理由                                                                                      |
| ---------------------- | ------ | ----------------------------------------------------------------------------------------- |
| 不可达工具             | 6 个   | 不在任何 agent 白名单里，模型永远调不到（内容已由 content-index 那套覆盖）                |
| `rag/retriever.ts`     | 1 文件 | 三个工具全部不可达                                                                        |
| 专家包装层             | 7 文件 | `expert/index.ts` + 6 个纯透传 `*-agent.ts`，零消费者且重复了 `AGENT_TOOL_CONFIGS` 的路由 |
| `@deprecated` 兼容导出 | 8 个   | 零消费者                                                                                  |

工具面 **16 → 10**，并新增一条断言：注册的工具必须至少出现在一个白名单里、白名单里的名字必须已注册（双向一致）——这类"悄悄不可达"的问题以后不会再无声发生。

### 8. 架构边界由测试守住

- 只有 harness 可以 import `orchestratorGraph`
- 只有 orchestrator 可以 import `supervisorGraph`
- `_core` 不得 import `agents`（入口 index.ts 除外）
- 活动代码不得 import `legacy`

每条都用真实违规验证过"它确实会失败"。

## 四、产品侧：3D 简历变成了什么

Agent 能力最终落在这几个用户可见的变化上：

| 能力              | 用户看到什么                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 流式 + 思考可视化 | 等待时显示**真实工具步骤**（"正在查阅完整简历档案"），回答**逐字**打出，随时可取消                                                   |
| 多专家协作        | 跨领域问题时显示协作时间线（头像 + 进行中/完成），最终答案是**真实综合**而非拼接，失败时降级为带归属的分段（绝不改写专家原文）       |
| 内容卡片          | 回答尾部出现可点卡片（作品/博客），slug 必须过内容索引校验，模型不参与生成                                                           |
| 房间内容化        | 每个房间列出真实作品/博客（内容文件用 `rooms:` 标注归属），空房间给引导语                                                            |
| 主动导览          | 进入房间后房间自己介绍（模板拼接、**零 LLM 调用**），每房间一次、可关闭、不打断聊天                                                  |
| 访客进度          | minimap 区分当前/已访问/未访问；推荐优先未访问房间；agent 也知道访客看过什么                                                         |
| 记忆              | 关掉再开聊天，服务端恢复上次对话                                                                                                     |
| 语音输入          | 录音 → 转写文本填入输入框（可编辑后再发），未配置服务时优雅降级                                                                      |
| 对话导出          | 一键导出 Markdown（含回答者显示名，不泄漏内部 id）                                                                                   |
| 内容运营化        | 简历摘要改从 markdown 读取，**删掉了 126 行硬编码 TS 常量**——UI 与 AI 终于共用一份事实源                                             |
| 健壮性            | 无 WebGL 时降级为文字版档案馆；真实加载进度条；三处动画遵循 reduced-motion                                                           |
| 移动端            | 房间面板改底部抽屉、引导面板隐藏、简历入口移到页脚                                                                                   |
| 地图修复          | 角色移动帧率无关、模型单次克隆、去掉空转的阴影贴图；标签层叠修复（过去会盖住聊天弹窗）；hover 手型光标与点击命中优先级；重置视角按钮 |
| 资源清理          | 删掉 25 个从未被引用的模型文件（1.89MB），models 目录 9.5MB → 7.6MB                                                                  |

## 六、过程中修掉的真实缺陷

| 缺陷                                 | 性质                                                                                                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **流式请求把自己取消、随后进程崩溃** | 生产级缺陷：`req.on("close")` 在请求体解析完就会触发（不是客户端断开），导致每次流式请求立刻取消；且守卫的 rejection 在 race 挂载前无人处理 → unhandledRejection 杀掉 API 进程 |
| **SSRF 面**                          | 语音转写旧入口拿调用方给的 URL 直接 fetch；该入口零消费者，直接删除并改为 base64 入口                                                                                          |
| **反向依赖**                         | 专家层需要发事件 → 事件汇不能放在 harness；同时发现 `_core/observability/langsmith-feedback.ts` import 了 `agents`（死代码）                                                   |
| **测试污染**                         | 新 describe 缺 `beforeEach` 导致 mock 调用计数跨测试累积（`clearAllMocks` 也不清 Once 队列）                                                                                   |
| **层叠 bug**                         | drei `Html` 默认 zIndex 极大，房间标签会盖住聊天弹窗                                                                                                                           |
| **测试耦合**                         | 语音测试通过被测函数验证 prompt 组装，删除旧入口时把测试一起带红                                                                                                               |
| **注入方式**                         | 模拟"SSE 中途断流"必须用 `pull()` 里 error（`start()` 同步 error 会抛出构造函数）                                                                                              |

## 七、验证方式与口径

- `pnpm check`（生产代码）+ `pnpm check:tests`（含测试）双门禁，全程保持干净
- **44 个测试文件 / 397 个测试全绿**，关键改动均补充了针对性用例（事件顺序、取消、预算、会话往返、卡片校验、路由推荐、语音各分支、简历解析、WebGL 降级…）
- e2e（Playwright）在真实浏览器里验证；本机负载高时出现的失败，均用"基线 A/B + 复跑"区分环境与代码
- 边界测试与守卫断言都用**故意违规**验证过会失败
- 事后复盘：**有一个缺陷现有测试抓不到**（流式路由的 Express close 语义），已补回归用例
